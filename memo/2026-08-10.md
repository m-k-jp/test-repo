---
title: 型検査が走っていなかった話
tags: [Astro, TypeScript, CI]
---

TypeScript で書いているのに、型検査が一度も走っていなかった。ビルドは通るし表示も正常だったので、しばらく気づけなかった。

## 何が起きていたか

TypeScript のビルドは、実は分離できる2つの仕事からできている。

| 仕事 | 内容 | 必要なもの |
|---|---|---|
| 型検査 | 型が矛盾していないか静的解析する | 型システム全体の理解 |
| トランスパイル | 型注釈を削って JS にする | 構文の把握だけ |

歴史的には `tsc` が両方をやっていた。しかし2つ目は「`:` から次の区切りまでを機械的に削る」だけなので、型の意味を一切理解しなくても実行できる。

そこに目をつけたのが esbuild や Oxc といった Rust・Go 製のツールで、2つ目だけを担当することで大幅に高速化した。Vite もこれを採用している。

代償として、1つ目が誰にも実行されなくなった。

```
従来:  tsc  →  型検査 ＋ トランスパイル
現代:  Vite →         トランスパイルのみ
```

## 確かめてみる

わざと明白な型エラーを2つ仕込んでビルドした。

```ts
export function broken(): string {
  return 12345;                          // string を返すはずが number
}
export function broken2(entry: Memo): string {
  return entry.data.nonExistentField;    // 存在しないプロパティ
}
```

結果は `Complete!`。素通りだった。

## Python と同じ構図だった

Python で `def f(x: int)` と書いても、`f("文字列")` は普通に動く。注釈は実行を拘束しないので、`mypy` を別途走らせないと意味がない。

TypeScript も同じで、型はコンパイル時に消える。違うのは「検査するのが当たり前」という文化があることだが、ビルドツールが速度のために検査を外した結果、**TypeScript を書いているのに mypy を走らせていない Python** と同じ状態が容易に起きる。

## 検査を入れたら本物のバグが出た

`astro check` を導入したところ、仕込んだ分を除いても7件のエラーが残った。すべて同じ原因だった。

```ts
const { entry } = Astro.props;   // entry の型が unknown
```

Astro は、そのファイル内に `Props` 型が宣言されている場合にだけ `Astro.props` に型を付ける。宣言を書いていなかったので、**そのファイル全体で型の恩恵がゼロ**になっていた。

```ts
interface Props {
  entry: CollectionEntry<'memo'>;
}
```

これで解消した。

## 教訓

動作は正常だった。ページは正しく生成され、公開もされていた。それでも `entry.data.titel` のようなタイポがあれば、エラーも出さずに `undefined` が表示されていたはずだ。

型検査が捕まえるのは**落ちるバグではなく、静かに間違うバグ**だと実感した。落ちるバグは動かせば分かるが、静かに間違うバグは目視でしか見つからない。

結局こういう関門にした。

| 段 | 仕組み |
|---|---|
| 手元 | `npm run verify` |
| push 時 | pre-push フックが自動で検査 |
| CI | ワークフローのステップ（迂回不可） |
